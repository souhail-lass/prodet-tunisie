# Internationalization (i18n) — Prodet Platform

> Status: Draft. Owner: Souhail. Last updated: 2026-05.
> Related ADR: [adr/0005-i18n-strategy.md](adr/0005-i18n-strategy.md).

## Locales

| Locale | URL segment | Direction | Default | Content completeness target at MVP |
|---|---|---|---|---|
| French (Tunisia) | `fr` | LTR | yes | **Complete** — all marketing pages, all UI strings, all visible product short descriptions. |
| Arabic (Tunisia) | `ar` | RTL | no | UI shell complete; key marketing pages (`/`, `/secteurs`, `/devis`, `/contact`, legal) translated; long product descriptions may show "[Traduction en cours]" placeholders. |
| English | `en` | LTR | no | UI shell complete; same key pages translated; long product descriptions may show placeholders. |

**Adding a new locale is a deliberate decision.** No automatic addition.

## URL strategy

- All routes are prefixed with the locale: `/fr/...`, `/ar/...`, `/en/...`.
- Root `/` redirects to the user's preferred locale (Accept-Language) with a fallback to `/fr/`.
- The locale switcher preserves the current path and query.
- `hreflang` alternate links emitted on every page for SEO.
- `lang` and `dir` attributes set on the `<html>` element per locale.

## Tooling

- **`next-intl`** as the i18n provider.
  - Server-component-aware (uses `getMessages()` / `getTranslations()` in RSC).
  - Namespaced messages (`common`, `home`, `catalog`, `quote`, `admin`, …).
  - Type-safe message keys via codegen (run on `pnpm dev` and CI).
- **Tailwind RTL** via `tailwindcss-rtl` (or built-in logical properties where possible) for `ar`.
- Layout uses CSS logical properties (`margin-inline-start`, `padding-inline-end`) to minimize per-direction overrides.

## File layout

```
src/
  i18n/
    request.ts                 # next-intl request config
    routing.ts                 # locale list + default
  messages/
    fr/
      common.json
      home.json
      catalog.json
      quote.json
      contact.json
      admin.json
      legal.json
    ar/
      ...
    en/
      ...
```

- One JSON namespace per file. Keep files under ~200 keys.
- Keys are dotted, descriptive in English: `home.hero.title`, `catalog.filter.category.label`.
- ICU MessageFormat for plurals and gender (`{count, plural, one {# produit} other {# produits}}`).

## Glossary and translation discipline

- A central glossary lives in [../00-overview/glossary.md](../00-overview/glossary.md) with FR/AR/EN equivalents for domain terms.
- Translation rule: when a translator is uncertain, keep the FR term inline with the AR/EN copy rather than guessing a wrong term. This is a B2B audience; better untranslated than mistranslated.
- All translations are reviewed by Souhail (or the named translator) before merge. **No auto-translation in production.** AI-drafted translations are allowed in the editor flow but must be human-reviewed.

## Product names — the special case

Product naming is **bilingual at the data layer**, not just at the UI layer.

- `product.name_canonical` — the official Swiver name. Usually French, sometimes mixed.
- `product_translation(product_id, locale)` — name + descriptions per locale.
- `product_alias.alias_text` — any string a customer or staff member uses, in any language. Critically, mixed-language aliases ("javel BIDON 5 لتر") are stored as-is — **no transliteration, no normalization beyond case + diacritics**.
- The matching engine normalizes both sides identically (lowercase, unaccent, trim, collapse whitespace) before comparing.

For display:

- The catalog shows `product_translation.name` for the requested locale, falling back to FR.
- The internal console always shows `name_canonical` alongside the localized name so Mère/Sœur recognize what is in Swiver.

## RTL specifics

- Direction switch happens at the document level via `dir="rtl"` on `<html>` for `ar`. Tailwind logical utilities handle most layout flipping.
- Icons that imply direction (chevrons, arrows) are mirrored or replaced for RTL.
- Mixed-content runs (a French phrase inside an Arabic paragraph) use `<bdi>` or directional embedding to keep numerals and Latin words readable.
- Numerals: use Western Arabic numerals (0–9) by default in Tunisian Arabic UI. Eastern numerals (٠–٩) only if the user community prefers them — confirm at content-review time.
- Forms: input alignment follows direction; `placeholder` text is direction-aware.
- Tables: column order is logically preserved; visually mirrored.

## Fonts

[Spike 6](../06-spikes/spike-arabic-rtl.md) finalizes the choice. Candidates:

- **Latin (FR/EN)**: Inter, or Geist Sans (Vercel default), or system UI sans.
- **Arabic**: IBM Plex Sans Arabic (matches Inter weight feel) or Noto Naskh Arabic (more traditional). Whichever harmonizes with the Latin choice for mixed runs.

Fonts are self-hosted via `next/font` (no third-party CDN). Subsetted to needed code blocks for performance.

## SEO

- `hreflang` for `fr-TN`, `ar-TN`, `en` on every alternate URL.
- `<html lang="..." dir="...">` set per locale.
- Canonical URLs point to the in-locale version, not the root.
- Sitemap split by locale: one sitemap per locale + a sitemap index.
- OpenGraph titles/descriptions translated per locale.
- JSON-LD `Organization` once; `Product` per locale.

## Currency and formatting

- Currency: TND (dinar tunisien). Format: `1 234,567 TND` (FR), `1,234.567 TND` (EN), `١٬٢٣٤٫٥٦٧ د.ت` style if Eastern numerals chosen for AR (decision at content-review time).
- Dates: `Africa/Tunis` timezone. Display in locale long format (e.g. "12 mai 2026", "May 12, 2026", "12 ماي 2026").
- Phone numbers: E.164 storage; locale-agnostic display with `+216` prefix.

## Address and contact

- Address always rendered per Tunisian convention (street + neighborhood + postal + city + country).
- WhatsApp deep links: `wa.me/216XXXXXXXX` regardless of locale.

## Operational notes

- Adding a translation does not require a deploy: messages are bundled at build time today (so it does require a build), but moving to runtime-loaded messages is a Phase 2 consideration if a non-developer needs to author copy.
- Missing-key handling: dev = warn loudly; production = render the key path (so the gap is visible) rather than empty. Sentry breadcrumb on missing key.
